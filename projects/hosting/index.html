About this guide

Written from the real setup of www.9a3why.space (a static amateur-radio site served from a small Linux PC at home). Unofficial: it describes one working way, not the only way. Created by 9A3WHY with the assistance of Claude, an AI assistant by Anthropic. License: CC BY-SA 4.0.

What you will end up with

  • A website on your own domain, served from a computer in your home
  • No open ports on your router and your home IP address not exposed to visitors
  • A firewall, automatic security updates, an uptime alert, and a repeatable "update the site" command
  • Your site files in a git repository, so nothing lives only on one machine

How it fits together

visitor
-> Cloudflare (HTTPS and caching)
-> encrypted tunnel (your computer connects OUT to Cloudflare)
-> cloudflared (small program on your computer)
-> nginx (web server, listens on 127.0.0.1:80 only)
-> /var/www/yoursite (your files)

Your PC makes an outbound connection to Cloudflare, so you do not open or forward any port on the router.

Placeholders used below. Replace them with your own values and never paste them literally: example.com (your domain), youruser (your Linux user), yoursite (a folder name), 192.168.1.0/24 (your home network, check yours with ip -4 addr).

0. What you need

ItemNotes
A computer that can run 24/7An old PC, a mini PC or a Raspberry Pi 4/5 is plenty for a static site
LinuxThese steps use Debian (13 "trixie"); Ubuntu is nearly identical
A domain nameAbout 10-15 EUR/year from any registrar
A free Cloudflare accountProvides DNS, HTTPS, caching and the tunnel
A GitHub accountOptional but recommended, for the site repository (private is fine)
A free healthchecks.io accountOptional, for "your site is down" alerts

You need a normal home internet connection. No static IP and no router changes are needed. Check your internet provider's terms about running servers at home; a small static site is usually fine.

1. Prepare the server

Install Debian (a minimal install with "SSH server" and "standard utilities" is enough), then:

shell
sudo apt update && sudo apt upgrade -y
sudo apt install -y nginx git curl ufw unattended-upgrades

Give the machine a fixed address on your home network (a "DHCP reservation" in your router's settings is the easiest way) so it does not change.

2. Your site files and the web root

Keep two separate folders:

  • the git repository where you edit: ~/yoursite
  • the web root that nginx serves: /var/www/yoursite

Keeping them separate means a mistake in the repository (a stray file, a draft) is never public. Updates are an explicit copy step (section 8).

shell
mkdir -p ~/yoursite && cd ~/yoursite
git init -b main
printf '<!doctype html><title>Hello</title><h1>It works</h1>\n' > index.html
sudo mkdir -p /var/www/yoursite
sudo cp index.html /var/www/yoursite/
sudo chmod -R a+rX /var/www/yoursite

chmod -R a+rX matters: if nginx cannot read a file you get a 403, and it is the most common beginner problem.

3. nginx: serve the site on localhost only

Create /etc/nginx/sites-available/yoursite:

nginx
server {
    listen 127.0.0.1:80 default_server;
    server_name _;

    root /var/www/yoursite;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}

Enable it, disable the default page, test, reload:

shell
sudo ln -s /etc/nginx/sites-available/yoursite /etc/nginx/sites-enabled/yoursite
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
curl -s http://127.0.0.1/ | head -3

listen 127.0.0.1:80 means nginx accepts connections only from the machine itself. The tunnel (next section) is the only way in from the internet.

4. Put the domain on Cloudflare and create the tunnel

  1. In Cloudflare, add your domain and follow the instructions to change the nameservers at your registrar. Wait until Cloudflare shows the domain as active.
  2. In the Cloudflare dashboard open Zero Trust (the "Cloudflare One" section) and go to Networks -> Tunnels -> Create a tunnel, type Cloudflared. Menu names change from time to time; look for "Tunnels".
  3. Name it (for example home-server). Choose Debian, 64-bit and copy the install commands the dashboard shows. Run them on your server. They add Cloudflare's package repository, install cloudflared and register it as a service with a token.
  4. Add a public hostname: subdomain www (and a second one with an empty subdomain for the bare domain), domain example.com, service type HTTP, URL localhost:80. Cloudflare creates the DNS records for you.

Check that the service runs and survives reboots:

shell
systemctl is-enabled cloudflared && systemctl is-active cloudflared

Then open https://www.example.com. You should see your test page with a valid HTTPS certificate, without having touched your router.

Make the tunnel start reliably after a reboot. Add an override so it waits for the network and restarts itself:

shell
sudo systemctl edit cloudflared
ini
[Unit]
After=network-online.target
Wants=network-online.target

[Service]
Restart=always
RestartSec=10

Save, then sudo systemctl restart cloudflared.

Treat the tunnel token like a password. It is the key to your tunnel; never put it in a git repository or a screenshot.

5. Firewall

Because nothing needs to reach your server from outside, the firewall can block all incoming traffic:

shell
sudo ufw default deny incoming
sudo ufw default allow outgoing

If you want to log in over SSH from another computer in your home network, allow it from the home network only, before enabling the firewall:

shell
sudo ufw allow from 192.168.1.0/24 to any port 22 proto tcp
sudo ufw enable
sudo ufw status verbose

If you only ever work at the machine's own keyboard, skip the SSH rule and switch SSH off completely (next section).

6. SSH: key first, then close the password door

Never turn password login off before a key works, or you lock yourself out. Order matters.

On your own computer (not the server):

shell
ssh-keygen -t ed25519 -C "my-laptop"      # choose a passphrase
ssh-copy-id youruser@server-address
ssh -o PasswordAuthentication=no youruser@server-address echo KEY_OK

Only when that prints KEY_OK (and does not ask for the account password), on the server:

shell
sudo tee /etc/ssh/sshd_config.d/00-hardening.conf >/dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
EOF
sudo sshd -t && sudo systemctl reload ssh
sudo sshd -T | grep -Ei "^(passwordauthentication|permitrootlogin)"

Keep your current SSH window open and test a new login before you close it. The file name starts with 00- so it is read first; sshd uses the first value it finds. Check the real state with sshd -T, not just the config file: another file may override your setting. (This was exactly our experience: we believed password login was off and it was not.)

If you do not use SSH at all, turn it off:

shell
sudo systemctl disable --now ssh ssh.socket
sudo ss -ltn | grep -E ":22\b" || echo "port 22 closed"

7. Automatic security updates

shell
sudo apt install -y unattended-upgrades
sudo tee /etc/apt/apt.conf.d/20auto-upgrades >/dev/null <<'EOF'
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
EOF
sudo systemctl enable --now unattended-upgrades
sudo unattended-upgrade --dry-run 2>&1 | tail -5

This installs security updates only and does not reboot by itself. Reboot manually about once a month (/var/run/reboot-required tells you when one is needed). Software from third-party repositories (such as cloudflared) is not covered; update it now and then with sudo apt update && sudo apt upgrade.

8. Updating the site: one command

Keep this script as scripts/deploy.sh in your repository:

shell
#!/usr/bin/env bash
set -euo pipefail
WEB=/var/www/yoursite
REPO="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
cd "$REPO"
if [[ "${1:-}" == "--pull" ]]; then git pull --ff-only; fi

# publish ONLY what visitors should see (list your own files and folders)
sudo cp -r index.html "$WEB"/
sudo chmod -R a+rX "$WEB"

code=$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1/ || true)
if [[ "$code" == 200 ]]; then echo "DEPLOY OK"; else echo "FAILED: HTTP $code"; exit 1; fi
shell
chmod +x scripts/deploy.sh
scripts/deploy.sh

Add more folders to the cp line as your site grows (gallery, img, ...). Do not publish README.md, .git, scripts or notes.

After a deploy, hard-refresh your browser (Ctrl+Shift+R). If you changed a CSS or JS file and the old one still shows, rename the file or add a version, e.g. style.css?v=2, and purge the Cloudflare cache (Caching -> Configuration -> Purge).

9. nginx hardening (optional but cheap)

Create /etc/nginx/snippets/yoursite-hardening.conf:

nginx
server_tokens off;

add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;

gzip on;
gzip_vary on;
gzip_types text/plain text/css application/javascript application/json image/svg+xml;

location ~* \.(webp|jpg|jpeg|png|svg|ico)$ {
    expires 30d;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
}
location ~ /\. { deny all; }

Add this line inside your server { } block, then test before reloading, and keep a backup outside sites-enabled:

nginx
    include snippets/yoursite-hardening.conf;
shell
sudo cp /etc/nginx/sites-enabled/yoursite ~/yoursite.nginx.bak
sudo nginx -t && sudo systemctl reload nginx
curl -sI http://127.0.0.1/ | grep -Ei "server:|x-content|x-frame"
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/.git/config    # 403 or 404, never 200

(add_header lines are repeated inside the location blocks because nginx does not inherit them once a location defines its own.)

10. Know when it breaks: an uptime check

On healthchecks.io create a check with a 5-minute period and a grace time of about 10 minutes. Copy its ping URL. Then:

shell
mkdir -p ~/bin
cat > ~/bin/healthcheck.sh <<'EOF'
#!/usr/bin/env bash
# ping only if the local site answers AND the services run
curl -fsS -m 5 -o /dev/null http://127.0.0.1/ || exit 1
for s in nginx cloudflared; do systemctl is-active --quiet "$s" || exit 1; done
curl -fsS -m 10 --retry 3 -o /dev/null "PASTE-YOUR-PING-URL-HERE"
EOF
chmod 700 ~/bin/healthcheck.sh
( crontab -l 2>/dev/null; echo '*/5 * * * * /home/youruser/bin/healthcheck.sh' ) | crontab -

Replace the placeholder text inside the script with your real ping URL in the script file only. It must never go into git. If the machine or tunnel goes down, the pings stop and healthchecks.io emails you.

11. Private tools: keep them behind a login

If you also run a private web app (a dashboard, an AI chat, a monitoring page), do not just publish it. In Cloudflare Zero Trust -> Access -> Applications -> Add -> Self-hosted, enter its hostname and add a policy that allows only your email address (one-time PIN login). Visitors then get a login page before they can reach the app. Also change the app's own default password and turn off anonymous access.

12. Back it up (do this before you need it)

The 3-2-1 rule: 3 copies, on 2 kinds of storage, 1 off-site.

  • Copy 1: the working files on the server.
  • Copy 2: your git repository on GitHub (a private repo is fine). This protects the site itself.
  • Copy 3: an encrypted copy of server settings and app data in cloud storage (for example with rclone and its crypt remote), plus an occasional manual copy to a USB drive.

Things worth saving besides the site: /etc/nginx, /etc/cloudflared, your cron jobs (crontab -l), your scripts, and the data of any apps you run. A backup you have never restored is only a hope. Do a test restore once.

Never commit secrets (.env files, tokens, keys, backups) to git. Start your repository with a .gitignore such as:

.env*
*.pem
*.key
*.log
*.db
*.tgz
*.tar.gz
*.bak
backups/
*.zip

13. GitHub, the practical bits

shell
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
git remote add origin https://github.com/youraccount/yoursite.git
git add -A && git commit -m "First version"
git push -u origin main

GitHub does not accept your account password for git push over HTTPS. Create a personal access token (GitHub -> Settings -> Developer settings -> Personal access tokens) and enter it when asked for the password. Tag your releases so you can always go back: git tag -a v1.0.0 -m "Version 1.0.0" && git push origin v1.0.0.

14. The final test: reboot

A server that only works until the next reboot is not finished. When everything above is in place:

shell
sudo reboot

After it is back (give the tunnel a minute):

shell
systemctl is-active nginx cloudflared ufw unattended-upgrades
sudo ufw status | head -3
curl -s -o /dev/null -w "local %{http_code}\n" http://127.0.0.1/
curl -s -o /dev/null -w "public %{http_code}\n" https://www.example.com/

Everything should say active, Status: active and 200.

If you want to host via GitHub Pages

A static site does not need your own server at all. GitHub Pages publishes the files of a repository as a website, for free, with HTTPS and no machine to look after. If your site is plain HTML, CSS and JavaScript, this is the easiest way to host it, and you can skip the server sections (1 to 7 and 9 to 10) of this guide.

  1. Put the site files in a repository (section 13). On a free GitHub account the repository must be public; a private repository needs a paid plan. Never commit secrets.
  2. Turn Pages on. In the repository open Settings -> Pages, choose the branch (usually main) and the folder to publish (the root or /docs). After a minute the site appears at https://youraccount.github.io/yoursite/.
  3. Use your own domain (optional). Enter it under Custom domain. At your DNS provider add a CNAME record for www pointing to youraccount.github.io. For the bare domain add the four A records 185.199.108.153, 185.199.109.153, 185.199.110.153 and 185.199.111.153 (check GitHub's Pages documentation in case they have changed). Then tick Enforce HTTPS.
  4. Update by pushing. Every push to the published branch updates the site within a minute or two.

Know the limits. A site of about 1 GB at most, a soft bandwidth limit of about 100 GB per month, no custom response headers, no server logs of your own, and static files only (no PHP or server code). On a free account your files are public. This site itself is served from Cloudflare's network from a GitHub repository, which also needs no server of your own and works with a private repository.

Checklist

  • nginx listens on 127.0.0.1 only; sudo nginx -t is clean
  • Domain is active on Cloudflare; tunnel runs and is enabled at boot; HTTPS works
  • No router port forwarding
  • ufw is active, default deny incoming
  • SSH: a key works before passwords are disabled (or SSH is switched off)
  • Unattended security updates are on; a monthly reboot is in your calendar
  • One-command deploy script; only public files are copied to the web root
  • .git, README.md, scripts and notes are not reachable from the web (403/404)
  • Uptime check is pinging; the ping URL and tunnel token are not in git
  • Private apps are behind Cloudflare Access
  • Repository on GitHub; at least one off-site (encrypted) backup, and a restore tested
  • A reboot test passed

Mistakes we actually made (so you can skip them)

What happenedLesson
Pasted PID 1234 or <your-file> literally into a commandReplace every placeholder before you run a command
cp: cannot stat 'index.html'The files were not unpacked or you were in the wrong folder; run ls first
A long block of commands ran after the first one failedJoin steps with && so the chain stops at the first error
"Author identity unknown" on the first git commitSet user.name and user.email once (section 13)
git push refused the account passwordUse a personal access token
Gallery looked broken after an updateOld CSS/JS stayed cached against new HTML; rename the files or add ?v=N, then purge the cache
Believed SSH was key-only when it was notCheck the effective setting with sudo sshd -T, and test with -o PasswordAuthentication=no
Deploy check expected 404 for .git but got 403After hardening, dotfiles return 403; both mean "not served"
A tag was pushed before the files were committedCommit and push first, tag last

Good habits

  • Change one thing at a time, test, then continue. Keep a backup of any config before you edit it (store it outside the folder nginx reads).
  • Write down what you changed. A short README.md and a changelog in your repository save hours later.
  • Keep secrets out of screenshots, chats and git. If one leaks, replace it (new token, new ping URL, new password) rather than hoping.
  • Photos and personal content: decide your license deliberately. Creative Commons licenses cannot be revoked once others used the material.
